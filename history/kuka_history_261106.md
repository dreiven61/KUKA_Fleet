**PostgreSQL에 보관합니다. 별도로 조회할 수 있습니다.** 현재 서버 설정과 설치본 코드를 확인했습니다.

작업 DB는 **`krcs-basic-data-db:5432`의 `wcs` DB**입니다. 설치본 DAO에서 확인한 테이블은 다음과 같습니다.

| 내용 | 현재 작업 테이블 | 이력 테이블 |
|---|---|---|
| 운송 전체 | `t_workflow` | `t_workflow_history` |
| 운송 내부 작업 | `t_workflow_task` | `t_workflow_task_history` |
| 세부 실행 단계 | `t_workflow_task_detail` | `t_workflow_task_detail_history` |

현재 테이블에도 완료 작업이 남을 수 있으므로, **현재 테이블에 있다는 것과 진행 중이라는 것은 다릅니다.** 상태값을 함께 봐야 합니다.

DB에 접속하면 COMMANDID로 이렇게 찾을 수 있습니다.

```sql
SELECT id, task_code, workflow_status, create_time, complete_time
FROM public.t_workflow
WHERE task_code = 'B07DCDED36CF4B3BAC744A938E668D65';

SELECT *
FROM public.t_workflow_history
WHERE task_code = 'B07DCDED36CF4B3BAC744A938E668D65';
```

접속 방법은 두 가지입니다.

- **API:** 지금 바로 사용 가능. `POST /interfaces/api/amr/jobQuery`에 `{"jobCode":"COMMANDID","limit":5}` 전송. 방금 작업 **6903·완료 상태30**이 조회되는 것까지 확인했습니다.
- **DB 직접 조회:** DBeaver·pgAdmin 등으로 가능하지만, 작업 DB는 현재 외부 포트가 열려 있지 않습니다. 내부 접속이나 SSH 터널이 필요합니다. **서버의 5434 포트는 다른 PostgreSQL**이므로 혼동하면 안 됩니다.

그리고 **SECS의 미확인 보고·재전송·중복 방지 정보는 우리가 만든 별도 파일 저널**에 저장합니다. Fleet 작업 DB와 MCS 보고 상태는 서로 구분됩니다.

DB 직접 SELECT는 아직 실행하지 않았습니다. 현재 SSH 계정에 Docker 접근 권한이 없어, 테이블 구조는 설치본 코드로 확인한 범위입니다.

> 유저가 통합 DB 관리한다고 다른 DB 쓰라고 하면 어찌함?

**요구가 ‘Fleet 자체 DB 교체’인지, ‘통합 DB에 작업 정보를 모으는 것’인지부터 구분해야 합니다.**

| 고객 요구 | 대응 |
|---|---|
| 고객이 관리하는 PostgreSQL로 Fleet DB 이전 | 버전·스키마·권한·백업·접속 설정을 검토하고 KUKA 지원 여부 확인 |
| Fleet DB를 MSSQL·Oracle 등으로 교체 | 접속 주소 변경만으로는 안 됩니다. DB 전용 SQL과 드라이버가 있어 KUKA의 공식 지원 확인 필요 |
| 통합 DB에서 현재 작업·실적을 관리 | Fleet API·이벤트를 받아 통합 DB에 저장하는 연동 방식으로 구현 가능 |

제가 제안하는 구조는 **Fleet이 운송 실행 상태를 관리하고, 고객 통합 DB에는 작업 접수·진행·완료 정보를 연동하는 방식**입니다.

우리가 만든 SECS의 작업·미확인 보고 저장부도 통합 DB로 변경할 수 있습니다. 다만 중복 방지를 위해 다음은 반드시 유지해야 합니다.

- COMMANDID와 보고 DATAID에 중복 방지 제약 적용
- 재기동 후 미확인 보고 복원
- 통합 DB 단절 시 접수·보고 보존 정책 정의
- 통합 DB에 작업이 안 보인다는 이유만으로 운송 재등록 금지

**통합 DB를 쓰는 것은 가능합니다. 하지만 Fleet 내부 DB 교체와 고객 DB 연동은 별도 작업이며, 내부 DB를 임의로 바꾸겠다고 약속하면 안 됩니다.**

**Oracle로 교체하는 방법은 있지만, 현재 Fleet에서는 설정 변경으로 끝나는 작업이 아닙니다. PostgreSQL을 완전히 제거하려면 Fleet 여러 서비스의 DB 처리 코드를 이식해야 합니다.**

설치본을 분석해 다음 의존성을 확인했습니다.

| 확인 항목 | Oracle 전환 시 필요한 변경 |
|---|---|
| `org.postgresql.Driver`, PostgreSQL JDBC URL | Oracle 드라이버·접속 설정으로 변경 |
| WCS와 Basic Data의 PostgreSQL 페이지 처리 고정 | Oracle 페이지 처리로 코드 변경 |
| `LIMIT` 53곳, 형변환 7곳, `DISTINCT ON` 등 | Oracle SQL로 변환 |
| 시퀀스 생성, `DELETE … RETURNING` | 번호 생성과 JDBC 결과 반환 방식 변경 |
| 빈 문자열 비교 9곳 | NULL 처리와 업무 조건 재검토 |

WCS에서 SQL 상수 **666개**를 찾았습니다. 모두 수정 대상이라는 뜻은 아니지만, 드라이버만 교체하는 수준이 아니라는 근거입니다. 특히 Oracle 19c는 빈 문자열을 NULL로 처리하므로 기존 화물 ID 조건을 그대로 옮기면 조회 결과가 달라질 수 있습니다. [Oracle 공식 설명](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Nulls.html)

Fleet 2.15 매뉴얼에는 ECS의 **Modbus, S7, TCP, HTTP, OPC UA, EtherNet/IP, ADS** 연동이 있습니다. 다만 이것이 현재 **KMP1500I 내장 리프트를 다른 PLC로 바로 대체할 수 있다는 뜻은 아닙니다.** 외부 PLC·주변 장치 연동과 차상 리프트 교체는 구분해야 합니다. [KUKA의 장치 연동 설명](https://www.kuka.com/amr-fleet)

```text
MCS → 기존 SECS 플러그인 → Fleet 작업

                              └─ 리프트 → 연동 인터페이스 → 새 PLC
```

새 PLC와 주고받을 정보는 최소한 다음이 필요합니다.

- 명령: 상승·하강·정지, 명령 식별번호
- 상태: 준비·동작 중·상승 완료·하강 완료·화물 유무·고장
