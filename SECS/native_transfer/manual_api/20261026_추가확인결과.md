## 별도 내장 E82 경로 발견

배포 레지스트리 `ecs-engine:kmres`의 코드에 다음 기능이 있다.

- `SecsClient.equipReceive`: Stream 2 / Function 49를 수신하면 헤더·본문·stream·function을 metadata로 담아 INBOUND_REQUEST를 규칙 엔진으로 넘긴다.
- `TbEnhancedRemoteCmdAckNode`: 설정된 TRANSFER 요청 본문의 필드를 추출하고 S2F50을 응답하는 코드가 있다.
- `TbGrpcApiCallNode`: 추출된 정보를 후속 API 호출에 사용하는 일반 규칙 노드가 있다.
- 사용자 화면에서도 Equipment → Device → New → Protocol Type에 E82가 실제 표시됨을 확인했다.

이는 기존 nav-secs:5555와 별개인 Fleet 내부 ECS 경로다. Windows 브릿지 프로그램 없이 구성할 후보지만, 아직 Rule Chain → 실제 From/To 운송 생성 → 완료 이벤트까지 검증한 것은 아니다. native Order Engine이 기존 New Sims를 인식하게 됐다는 뜻도 아니다. 두 경로의 설정과 Port 데이터가 자동 공유된다고 가정하지 않는다.

현재 GUI의 Setup은 Building Code·District·Device Name·Rule Name 필수값 검사를 한다. 따라서 E82용 Rule Chain을 먼저 준비해야 한다. 다른 용도의 Rule을 임의 선택하거나 E82 장치를 저장·Enable하지 않는다. 새 HSMS listener가 필요하다면 기존 5555와의 충돌 및 Docker 포트 접근도 검증해야 한다.

### 편집기 검색 주의점 확인

실제 서비스 로그 `/opt/server/logs/ecs/ecs_info.log`의 2026-10-26 시작 기록에도 `TbEnhancedRemoteCmdAckNode`의 `K_SECS` 등록이 있다. 현재 웹 `ruleDetail--Zy6BsBk.js`에서는 CUSTOM_DEVICE일 때 `K_BUTTON_BOX,K_SECS`를 포함하여 노드 목록 API를 요청한다. 따라서 클래스 파일의 존재 외에 실제 시작 시 등록과 현재 프런트엔드 요청 경로도 확인했다.

왼쪽 노드 검색은 `c.name.indexOf(t) != -1`을 사용하므로 **대소문자를 구분**한다. 영어 노드 이름은 `Enhanced Remote Command Acknowledge`다. 소문자 `secs`, `remote`, `enhanced`는 이 이름에 일치하지 않는다. 검색창을 완전히 지운 뒤 `Enhanced`로 검색한다. 또한 검색 구현이 이미 필터링된 목록을 다시 좁히므로, 다른 검색어로 바꿀 때도 먼저 완전히 비워 원본 목록을 복구한다. 이 검색 차이는 서버 설정 변경 없이 확인했다.

1. Equipment → Rule Chain Library의 New 화면에서 E82용 규칙 유형·노드를 확인한다.
2. TRANSFER 파라미터를 추출하는 규칙과 후속 운송 생성 API를 대조한다.
3. 장치 연결 설정, 오류 응답, 중복 COMMANDID, 실제 완료 이벤트 처리 범위를 정한 뒤 통신 시험을 진행한다.

이번 조사 중에는 운송 주문을 보내거나 로봇을 움직이지 않았다. 지도 변경은 사용자가 GUI에서 실행했고, 그 결과를 API로 조회했다.
