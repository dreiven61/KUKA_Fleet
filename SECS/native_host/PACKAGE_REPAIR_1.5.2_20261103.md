# 1.5.1 패키징 오류와 1.5.2 수정

2026-11-03. 1.5.1의 최종 전달 파일을 잘못 덮어쓴 패키징 오류다. 사용자가 발견한 용량 차이는 실제 의존성 누락이었다.

## 원인

정상 build.ps1은 자체 클래스 JAR 생성 → package_runtime.py로 런타임 병합 → 전체 시험 → 격리 플러그인 로딩 순서로 실행된다. 처음 전체 시험을 통과한 1.5.1은 13MB였다. 이후 설명문 변경을 반영하려고 jar cfm만 수동 실행해 런타임 병합 없이 같은 경로를 덮어썼다. 앞선 시험 결과가 최종 125KB 파일에 유효하지 않게 됐는데 전달 전에 재확인하지 않은 실수다.

| 파일 | 바이트 | 항목 수 | gRPC 항목 | SECS 항목 |
|---|---:|---:|---:|---:|
| 기존 1.5.0 | 13,175,186 | 7,765 | 3,238 | 393 |
| 잘못된 1.5.1 | 125,251 | 45 | 0 | 0 |
| 새 1.5.2 | 13,175,257 | 7,765 | 3,238 | 393 |

## 수정

- 1.5.0에서 제공하던 기능과 런타임을 유지하고 PortID/VehicleID 통일 변경을 포함해 1.5.2로 전체 재빌드했다. 1.5.0의 자체 클래스 파일도 모두 존재하며, 공통 런타임 7,720개는 바이트 내용까지 동일하다.
- verify_package.py가 JAR 손상·중복 항목·필수 클래스·gRPC/SECS 서비스와 버전 및 1.5.0 대비 파일 누락을 검사한다.
- 빌드는 런타임 병합 직후와 모든 시험 종료 후에 패키지를 검사한다. 두 시점 사이 SHA256이 바뀌면 실패한다. 시험 완료 파일의 정보는 `<JAR명>.verified.json`으로 저장한다.
- 잘못된 1.5.1은 `build/servostar-mes-transfer-1.5.1.jar.invalid`로 분리했다. 이 파일은 Import하지 않는다.

## 적용

Import 대상은 `SECS/fleet_transfer_plugin/build/servostar-mes-transfer-1.5.2.jar`다. MCS는 2.4.0을 그대로 사용한다. API 내부 Robot XML, 운송/보고 저널, MCS 작업 이력을 삭제하거나 초기화하지 않는다. 기존 작업·보고를 정리한 상태에서 사용자가 새 JAR를 Import/Enable하고 MCS를 재연결한다.

이번 작업은 로컬 빌드와 검증이며 서버 Import 또는 새 운송은 수행하지 않는다. 코드 동작과 ID 확인 방법은 [식별자 통일 적용방법](CANONICAL_ID_1.5.1_2.4.0_적용방법.md)을 따른다. 해당 문서의 기능 변경은 1.5.2에 포함된다.
