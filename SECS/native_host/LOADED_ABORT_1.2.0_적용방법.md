# 적재 ABORT 대기·회수반송 — 플러그인1.2.0 / Virtual MCS2.2.0

## 지원하는 시나리오

1. 입고 포트에서 화물을 적재한다. 실제 바코드 판독과 일치 여부 판단은 MCS/스캐너 측에서 수행한다.
2. 불일치 시 MCS가 기존 COMMANDID에 S2F41 `ABORT`를 보낸다.
3. 진행 중 리프트는 끝낸 뒤 원래 운송을 취소한다. 성공한 이적재에는 실패 알람을 만들지 않는다. 실제 ACTION_END 실패가 확인된 경우에만 시험용 이적재 실패 알람을 사용한다.
4. ABORT 완료201·차량 해제610 및 호스트 ACK를 확인한 뒤, 아직 적재 중인 차량을 **설정된 대기 노드까지 적재 상태로 이동**시킨다. 원래 작업·화물·스캔 기록은 지우지 않는다.
5. 대기 이동 작업 완료와 같은 차량의 적재·Idle·비점유·대기 노드 도착을 확인하면 시험용 CEID9004 `READY`를 보낸다.
6. MCS가 **새 COMMANDID**로 `TRANSFER`, `SOURCEPORT=AMR_2`, `DESTPORT=PORT_89`처럼 회수반송을 요청한다. 실제 차량 ID `2`도 SOURCEPORT로 받을 수 있다. AMR_1/2/3은 이 프로젝트의 명시적 표기이며 공식 SKI 고정 명칭이 아니다.
7. 화물을 실제 적재한 그 차량만 사용해 회수 포트로 이동·하차한다. 새 명령의 정상 완료207/Result0을 확인한다. 원래 ABORT를 정상 운송 완료로 바꾸지 않는다.

현재 회수 도착지는 기존 작업 포트10개 중에서 선택한다. 회수 명령을 미리 큐에 넣는 방식은 지원하지 않는다. READY 및 그 보고 ACK 전에 보내면 HCACK2와 CEID9003 사유로 거부한다. PC가 READY를 보자마자 전송해서 ACK 처리와 경합하면 같은 명령을 자동 반복하지 말고 거부 결과를 확인한 뒤 새 명령으로 요청한다.

바코드 불일치가 나도 Fleet 화물 ID를 실제 스캔 문자열로 임의 변경하지 않는다. 회수 CARRIERID는 **Fleet에서 그 AMR에 연결된 등록 화물 ID**여야 한다. 실제 리더 연결·화물 ID 정정은 이번 기능과 별도다. 시험용 CARRIER_SCAN_TEST도 실제 센서 판독이 아니다.

## 대기 위치 옵션

Fleet의 일반 자동 주차를 기다리는 대신, 플러그인에 `loadedAbortWaitNodes`를 명시한다. 설정이 없으면 적재 ABORT 자동 대기 이동은 비활성이다. **기존 이력의 ABORTED 작업을 설치 직후 이동시키지 않는다.** 이 설정이 활성화된 상태에서 새로 접수한 ABORT만 대상이다.

현재 설정 파일의 기존 토큰·포트·저널·알람 매핑 등은 유지하고 아래 항목만 추가한다. 기본 컨테이너 경로는 `/opt/nav/config/servostar-secs.json`, 기존 호스트 배치 경로는 `/opt/server/config/servostar-secs.json`이다. `servostar.secs.config`를 따로 지정했다면 실제 사용 파일을 수정한다.

```json
"loadedAbortWaitNodes": {
  "1": "lay01-dist1-103",
  "2": "lay01-dist1-105",
  "3": "lay01-dist1-102"
}
```

이는 현재 지도 대기 노드의 **예제**다. 실제 지도에 존재하고, 적재 화물까지 통행·정차할 공간이 있으며, 다른 차량과 충돌하지 않는 위치인지 확인한 뒤 사용한다. 차량별 대기 노드는 서로 달라야 한다. 충전소·충전 입구·작업 포트는 이 설정에서 거부한다. 설정 변경만으로 새로운 지도 노드나 경로가 만들어지지는 않는다.

대기 이동은 WCS에서 추적 가능한 별도 RACK_MOVE로 만든다. 화물을 계속 들고 있는 같은 차량과 현재 노드를 확인하고, 현재 위치의 UP 유지 단계 뒤 대기 노드에는 **하차 액션을 넣지 않는다**. 회수반송도 이 차량만 지정하며, 목적지에만 DOWN을 넣는다. 이미 적재한 차량의 시작 UP은 기존 적재 컨텍스트 유지를 위한 단계다. 새 픽업·CarrierInstalled 보고를 만들지 않는다. 직접 `robotMove`는 WCS 작업 추적을 우회하므로 이 구현에서 사용하지 않는다.

## 사용자 적용 순서

1. 새 운송·반복을 멈추고 활성 작업과 미보고 건이 없는지 확인한다. 적재 대기 이동을 사용할 AMR과 노드 매핑을 확정한다.
2. 설정 파일을 백업하고 위 옵션을 추가한다. JSON 쉼표와 문법을 확인한다. 기존 저널은 삭제하지 않는다.
3. 기존 SERVOSTAR-MES-TRANSFER를 Disable하고 `SECS/fleet_transfer_plugin/build/servostar-mes-transfer-1.2.0.jar`를 Import → Enable → STARTED 확인한다. STANDARD-API는 유지한다. 구버전을 동시에 Enable하지 않는다.
4. 기존 Virtual MCS를 종료하고 `VirtualMCS/실행.cmd` 또는 `VirtualMCS/dist-2.2.0/KukaVirtualMCS.exe`를 실행한다. 기존 `192.168.0.45:5556`, PC Active, Session3000을 유지한다.
5. TSC가 PAUSED라면 운송 RESUME으로 AUTO를 확인한다. 대기 이동이 진행 중이거나 결과 미확인인 동안에는 시스템 PAUSE/RESUME를 성공으로 가장하지 않고 HCACK2 `RECOVERY_WAIT_MOVE_ACTIVE`로 거부한다. 대기 이동 자체의 별도 SECS 제어는 이번 범위에 포함하지 않았다.
6. 가상 AMR에서 아래 시험을 순서대로 수행한다. 실제 차량 적용 전 별도 현장 검증이 필요하다.

이번 개발 작업은 서버의 설정·JAR·실행 중 Virtual MCS를 교체하지 않았다. 준비된 파일은 로컬 산출물이며 적용 완료나 현장 운전 검증을 뜻하지 않는다.

## 시험 순서

1. 화물을 적재하고 주행 중인 운송1건을 ABORT한다. 리프트 동작 중 ABORT도 별도로 시험한다. 현재 Fleet은 리프트 완료 후 취소하는 동작이다.
2. 원래 작업201/610을 ACK한다. 대기 이동 접수 후9004/MOVING, 실제 대기 도착 후9004/READY를 확인한다. 화물이 AMR에 남아 있어야 한다.
3. Virtual MCS FROM에서 **실제 차량 AMR_번호**, TO에서 빈 회수 포트를 선택하고 같은 CARRIERID로 새 전송을 한다.
4. 기존 차량이 그대로 반송하고, 회수 포트에서 하차하는지 확인한다. 새 운송은208/604/211/605와 목적지601/606/302/607/610/207을 보고한다. 새 픽업이 아니므로 출발지601·602·301·603은 보내지 않는다.
5. 새 운송의207/Result0과 실제 화물 배치를 확인한다. 원래 작업의9004/RETURNED는 회수 명령의 실제 완료 증거에 따라 생성된다.
6. 다른 차량·다른 화물·미도착 차량·점유 목적지·미확인 이전 작업으로 요청하면 전송 전에 거부되는지 확인한다.

## 상태와 복구 제한

인증된 POST `/interfaces/api/mes-secs/status`의 작업 항목에 `recoveryState`, `recoveryMission`, `recoveryNode`, `recoveryCommand`, `recoveryDetail`이 추가된다.

| 상태 | 의미 |
|---|---|
| MOVING | 대기 이동 API 접수, 도착 미확인 |
| READY | 같은 적재 차량의 대기 도착과 해제 확인 |
| CLAIMED | 새 회수 명령에 연결됨 |
| RETURNED | 새 회수 운송 정상 완료 확인 |
| NOT_LOADED | 원래 ABORT 후 실제 비적재·포트 배치 확인, 적재 이동 없음 |
| BLOCKED | 대기 노드 점유·실패·설정 또는 이적재 실패 등 확인 필요 |
| UNCERTAIN | 이동 요청 응답/재시작 결과 미확인, 자동 재실행 없음 |

MOVING인데 상태 조회가 일시 실패하면 확인 대기를 유지한다. 이동 요청을 보낸 뒤 응답을 잃거나 SENDING 중 재시작하면 UNCERTAIN으로 보존한다. BLOCKED/UNCERTAIN을 지우려고 저널을 삭제하거나 같은 이동을 새 ID로 재전송하지 않는다. 해당 recoveryMission의 Fleet 작업·차량·화물을 먼저 조회해야 한다. 현재 버전은 이 상태를 자동 해제하거나 대기 이동을 자동 재시도하는 기능을 제공하지 않는다.

READY 이후에도 수동 이동·다른 클라이언트 명령으로 차량이 바뀌면 회수 접수를 거부한다. 이 기능은 플러그인 외부의 모든 수동 배차를 잠그는 전역 예약은 아니다. 대기 노드는 적재 차량 전용으로 운영하고, 다른 프로그램이 해당 AMR에 명령을 보내지 않도록 운영해야 한다.

## 추가 보고 — 프로젝트 시험용

CEID9004 / RPTID93은 **공식 SKI 이벤트가 아닌 프로젝트 확장**이다. ACK는 S6F12 B[1]0, 기존 보고 큐와 DATAID 재전송 규칙을 사용한다.

```text
S6F11 W
L[3]
  U4 DATAID
  U2 9004
  L[1]
    L[2]
      U2 93
      L[6]
        A 기존_ABORT_COMMANDID
        A CARRIERID
        A 실제_VEHICLEID
        A 대기_노드_UUID
        A MOVING / READY / BLOCKED / UNCERTAIN / RETURNED
        A 상세_사유
```

회수 명령의 S2F49 구조는 기존과 같고 `TRANSFERINFO.SOURCEPORT`만 AMR_2 또는2처럼 지정한다. REPLACE0, 우선순위1~99, COMMANDID32자 이내 규칙은 유지한다. Virtual MCS 작업 메시지에9004를 별도로 표시하고, 회수 명령 완료 후 From/To 자동 교환은 하지 않는다.

## 검증 범위

로컬 회귀는 적재 대기·AMR 소유권·보고·재시작·응답 유실·정상 리프트의 잘못된 실패 알람 방지와 기존 기능을 검사한다. 설치된 STANDARD-API의 액션 생성 메서드도 로컬 호출해 대기 목적지에 암묵적인 DOWN이 추가되지 않는지 검사한다. 이는 실서버의 적재 대기 이동·회수반송 전체 시나리오를 실행한 증거가 아니다. 적용 후 위 가상 AMR 시험이 남아 있다.
