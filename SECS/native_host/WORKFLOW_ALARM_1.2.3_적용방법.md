# Fleet 작업 경고 발생·해제 보고 수정 - 1.2.3

2026-10-30. 플러그인 1.2.3 / 기존 Virtual MCS 2.2.0, 5556 / Session 3000 유지.

## 확인한 원인

가상 Fleet 작업 6899는 배차 전, 6900은 AMR 2 적재 후에 진입금지 영역 때문에 `jobQuery`의 `status=50, warnFlag=1, warnCode=200103`으로 대기했다. 차단 해제 후 `warnFlag=0` 및 정상 완료를 확인했다. 해당 작업 로그의 `subscribeMissionStatus` 메시지에는 `WARNING/WARN_CLEAR`가 없었다. 기존 플러그인은 그 콜백만으로 알람을 처리했으므로, 코드 매핑 추가만으로 이 누락을 해결할 수 없었다.

실제 조회 스냅샷 7개를 `fleet_transfer_plugin/test/fixtures/workflow_warning_20261030.json`에 보존했다. 원본 서버 시계는 2026-10-24, Windows 시계는 2026-10-30이다. 두 시각을 빼서 지연으로 계산하지 않는다.

## 수정한 동작

- 별도 감시 스레드가 Native SECS가 관리하는 미종결 작업 및 아직 경고가 남은 작업을 1초 간격으로 조회한다. 네트워크 조회 중에는 제어 상태 잠금을 잡지 않는다. 제어·운송을 재발행하지 않는다.
- 정확한 COMMANDID·화물·workflowId·알려진 차량과 일치하는 응답만 사용한다. `warnFlag=1`과 유효한 코드로 발생을 확인하고 `warnFlag=0`으로 해제를 확인한다.
- 응답 유실, 오류, 빈 목록, 중복 행, 식별 불일치, 미등록 상태값, 누락·비정상 warnFlag는 해제 근거로 사용하지 않는다. 플러그인 작업이 완료됐어도 기존 알람이 남으면 계속 해제를 조회한다.
- 동일 ALID가 유지되는 동안 S5F1 발생은 1회다. 여러 작업에서 같은 ALID가 발생하면 최초 발생·마지막 해제에 S5F1을 생성한다. 차량 번호가 확인된 경우에만 해당 차량의 702/701도 생성한다. 배차 전 경고에 가짜 AMR 번호를 붙이지 않는다.
- 기존 WCS 콜백과 조회 경로가 같은 ALID를 동시에 확인해도 발생 보고를 중복 생성하지 않는다. 다른 경로에 유효한 활성 상태가 남아 있으면 해제를 보류한다.
- 활성 상태와 보고는 기존 저널에 보존한다. 재시작 자체로 발생·해제를 만들지 않는다. ACK 유실 시 기존 보고를 재전송할 수 있으므로 수신측 중복 처리가 필요하다.
- 상태 API의 `state.activeAlarms`에서 ALID·원인 작업·차량·코드·수집 경로를 확인한다.

## ALID 시험 프로필

기존 `alarmMappings`에 명시된 매핑을 우선한다. 매핑이 없는 1~999999 숫자 작업 경고는 **프로젝트 시험용** `ALID=1000000+warnCode`, category 6, ALTX `TEST_FLEET_WORKFLOW_WARNING_<code>`를 사용한다. `200103`은 **1200103**이다. 이 값과 텍스트는 공식 SKI/KUKA 알람 명세의 할당값이나 오류 설명이 아니다.

1000001~1999999는 이 숫자 시험 프로필을 위해 예약한다. 동일 값에 다른 코드를 설정하면 시작 시 거부한다. 현장 MCS의 공식 ALID 계약이 정해지면 `alarmMappings`에 명시적으로 대응한다. 비숫자·미매핑 코드는 로그로 남기며 임의 해시 ALID를 만들지 않는다.

보고는 S5F1 발생(ALCD 0x86)/해제(ALCD 0x06), S5F2 ACK 0이다. 차량이 확인된 경우 S6F11 702/701, S6F12 ACK 0도 확인한다. 배차 전 경고는 S5F1/S5F2만 확인한다.

## 서버 적용

1. 미완료 운송·미확인 제어가 없는지 확인한다. 기존 저널·화물·작업을 삭제하지 않는다.
2. 기존 1.2.2 JAR를 백업하고 Plugin Management에서 Disable → Delete한다. STANDARD-API 2.15.5는 유지한다. 재시작 시 충돌하지 않도록 검색 폴더에는 같은 Plugin-Id의 구버전 JAR를 중복으로 남기지 않는다.
3. `fleet_transfer_plugin/build/servostar-mes-transfer-1.2.3.jar`를 Import → Enable한다. 기존 Virtual MCS를 재연결하고 S1F13을 확립한다. PC 교체·JSON 변경은 필요 없다.
4. `/interfaces/api/mes-secs/status`에서 `version=1.2.3`, `communicating=true`, `healthy=true`를 확인한다.
5. 가상 AMR에서 임시 진입금지 영역으로 같은 경고를 유도한다. 200103 발생 → S5F1 ALID1200103 발생 1회 → 20초 이상 유지 중 추가 발생 없음 → 영역 해제 → S5F1 같은 ALID 해제 1회와 각각의 ACK 0을 확인한다. 실제 차량이 확인된 경고에는 702/701도 각각 1회인지 확인한다.
6. 영역을 비활성화하고 기존 시험 운송의 207/Result0 및 ACK, 미확인 작업·보고가 없는지 확인한다. 시험용 영역은 비활성 상태로 보존할 수 있다.

## 검증 범위

로컬 검사는 실제 캡처 재생, 반복 감시, 오류·누락·식별 불일치, 종결 뒤 해제, 재발, 중복 수집 경로, 동시 경고 집계, 저널 재로드, 명시적 매핑, 실제 localhost HSMS의 발생·해제·ACK·순서를 포함한다. 기존 운송·회수반송 회귀 검사도 실행한다. 빌드 로그와 `build/validation_1.2.3.json`을 확인한다.

이 변경은 Native SECS가 소유한 작업의 작업 경고를 보완한다. AMR의 모든 하드웨어 알람·비상정지·오프라인 상태를 수집하는 전체 차량 알람 인터페이스를 구현한 것은 아니다. 1초 미만 경고가 조회 사이에 발생·해제되고 콜백도 없으면 감지하지 못할 수 있다. 서버 적용 및 실제 가상 Fleet의 새 보고 수신은 로컬 검사와 구분하여 기록한다.
