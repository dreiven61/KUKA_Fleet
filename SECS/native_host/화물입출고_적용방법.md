# 화물 입고·반출 / 다중 화물 시험본

실제 서버에 업로드하거나 로봇을 움직이지 않은 로컬 검증본이다.

## 사용자 시험 순서

`화물 입고·반출` 탭의 대상 CARRIERID는 위쪽 운송 입력과 공유한다. 화물 모델은 Fleet에 미리 정의돼 있어야 한다. 개별 화물 ID는 입고 시 생성할 수 있다.

1. **Fleet 화물 조회**: 현재 ID/포트/노드/모델/반입·적재 상태를 조회한다. 목록은 수신 시점 정보이며 자동 위치 감지나 실물 확인 결과가 아니다.
2. **새 화물 입고**: 실제로 비어 있는 작업 포트에 가상/실제 화물을 배치한 다음, 새로운 CARRIERID와 모델(기존 시험 모델은 `SIM_TRAY_001`), 입고 포트, 별도로 읽은 스캔 ID를 입력한다. 실제 배치 확인 체크 → 스캔 확인 후 입고.
3. 이력의 **CONFIRMED / INVENTORY_VERIFIED**와 후속 조회 결과를 확인한다. HCACK4는 최종 입고 완료가 아니다. 기존 ID가 반출 상태면 새로 생성하지 않고 재입고한다.
4. 목록에서 화물을 선택한다. ID와 현재 포트가 운송 입력에 반영된다. 비어 있는 도착 포트를 고르고 1회 운송한다. 임의 화물 ID를 입력해도 TRANSFER가 화물을 자동 생성하지 않는다.
5. 다른 화물에도 반복한다. 동일 화물의 미확인 운송은 중복 발행하지 않는다. 다른 화물은 별도 작업을 보낼 수 있고 Fleet이 AMR 1/2/3을 배차한다.
6. **반출**: 운송을 끝내고 실제 관리 영역 밖으로 반출한 뒤 ID·기존 포트를 확인한다. 배치 확인 체크 → 반출. 기본은 등록 유지(off-map)다. 영구 삭제가 필요할 때만 삭제 체크 및 확인창을 사용한다.
7. AMR이 목적지에 화물을 내려놓는 것은 드롭이며, Fleet 관리 영역 밖으로 나가는 반출과 다르다. 운송 완료마다 containerOut을 자동 호출하지 않는다.

신규 생성은 `containerIn isNew=true`, 기존 반출 화물의 재입고는 false다. 반출은 `containerOut isDelete=false`가 기본이다. 삭제 선택 시 true다. API의 position에는 매핑한 실제 `lay01-dist1-N` 노드를 보낸다. 조회 시 89/97의 외부 코드 `SECS_ST_89/97`도 포트로 인식한다.

## 거부와 미확인 처리

- 잘못된 ID/포트/SECS 자료형은 실행 전에 거부한다. ID/모델은 1~64자의 영문·숫자·`_ . : -` 범위다. 임의 충전·통과 노드는 입출고 포트로 쓰지 않는다.
- 이미 지도에 있는 동일 ID를 입고로 다른 위치에 덮어쓰지 않는다. 점유된 입고 포트, 적재 중인 화물, 출발지 불일치, 점유된 도착지는 거부한다.
- 입출고 전 Native Host가 소유한 작업뿐 아니라 Fleet의 Created/Executing/Waiting/Cancelling/Warning/Startup error 작업도 조회한다. 해당 화물이나 포트와 충돌하면 실행하지 않는다. 최대 1,000개 범위를 넘는 조회는 불완전한 정보로 진행하지 않는다.
- 입출고 API의 성공 응답 뒤 반출 상태까지 포함하는 containerQueryAll도 확인해야 CONFIRMED다. HTTP 응답 유실 또는 변경 뒤 조회 실패는 UNCERTAIN으로 남는다. 기존 요청 ID와 새 ID 모두 자동 우회 재전송하지 않는다.
- 조회로 실제 화물 상태를 확인한 뒤 UNCERTAIN 입출고 행을 선택하고 실제 배치 확인 체크 → **선택 미확인 건 결과 재확인**을 사용한다. 이 명령은 원래 입출고 POST를 반복하지 않는다. Fleet 현재 상태가 원래 요청 결과와 일치하고 충돌 작업이 없을 때만 CONFIRMED로 해제한다. 일치하지 않으면 미확인을 유지하며 작업자 판단이 필요하다.
- PC 기록은 `%LOCALAPPDATA%\ServoStar\KukaVirtualMCS\cargo-operations.jsonl`, 서버 기록은 기존 Native Host 설정의 journal이다. 재시작 후 미확인 건을 성공으로 만들거나 새 명령으로 자동 재전송하지 않는다.

## SECS 계약 — 사용자 정의 확장

다음 RCMD와 9000번대 이벤트는 **SKI/KUKA 표준 명령이라고 주장하지 않는 이번 시험용 확장**이다. S2F49 TRANSFER 여섯 필드는 유지한다.

S2F41 W 본문은 `L[2](A RCMD, L[n](L[2](A 파라미터명, 값), ...))`이다.
REQUESTID는 자동 생성 32자 GUID다. 같은 ID는 한 번만 처리한다.

| RCMD | 파라미터 |
|---|---|
| CARRIER_QUERY | REQUESTID A |
| CARRIER_IN | REQUESTID A, CARRIERID A, PORT A, MODEL A, SCANNEDID A, SCANOK U2(0/1) |
| CARRIER_OUT | REQUESTID A, CARRIERID A, PORT A, DELETE U2(0/1) |
| CARRIER_SCAN_TEST | REQUESTID A, CARRIERID A(기대 ID), PORT A, SCANNEDID A(판독 ID), SCANOK U2(0/1) |
| CARRIER_VERIFY | REQUESTID A, TARGETID A(재확인할 기존 입출고 REQUESTID) |

응답은 S2F42 `L[2](B HCACK,L CPACK)`이다. HCACK4는 명령 처리/결과 보고 대상으로 접수했다는 뜻이며 실제 입출고 성공 여부는 아래 결과로 확인한다. HCACK5는 이미 시도한 ID이므로 재실행하지 않는다.

- **CEID9001 / RPTID90**: `L[2](A REQUESTID, L[n](L[6](A CARRIERID,A PORT,A NODE,A MODEL,U2 IN_MAP,U2 CARRIED),...))`.
- **CEID9002 / RPTID91**: `L[6](A REQUESTID,A RCMD,A OUTCOME,A CARRIERID,A PORT,A DETAIL)`.
- OUTCOME은 CONFIRMED/REJECTED/UNCERTAIN. 조회는 9001 자체가 결과다. 원래 미확인 건 재확인 성공 시 원래 REQUESTID의 CONFIRMED와 재확인 요청 결과를 각각 보고한다.
- S6F11의 외부 구조는 기존과 같이 `L[3](U4 DATAID,U2 CEID,L[1](L[2](U2 RPTID, values)))`. PC는 저장/검증 뒤 S6F12로 응답한다. 기존 미보고 재전송/ACK 거부 시 중단 정책을 유지한다.

## 바코드 검증의 구현 범위

- 입고 시 **기대 ID와 별도 스캔 ID의 일치**, 판독 성공 입력을 요구한다. 스캔값을 기대 ID로 자동 채우지 않는다. 이 시험 프로필은 캐리어 라벨 ID=containerCode이고 입고 시 기본 검증 코드도 같은 값이다.
- `ID 판독 보고 시험`은 수동 입력으로 **CEID406 CarrierIDRead / RPTID14 L[3](A 판독ID,A CarrierLoc,U2 IDReadStatus)**를 만든다. 상태는 0 일치, 1 실패, 2 동일 ID가 다른 위치/차량에 등록된 중복 의심, 3 기대 ID 불일치다. 세 필드가 유효하며 구 사양서의 취소선 필드를 추가하지 않는다.
- 판독 시험은 Fleet 재고나 작업 완료 상태를 바꾸지 않고 운송을 발행하지 않는다. DB 조회만으로 자동 406 성공 보고를 만들지 않는다.
- **실제 바코드 스캐너 드라이버/설비 신호/차량 픽업 시점 판독/불일치 시 차량 정지 인터록은 이번 구현에 포함되지 않는다.** 화면에 실제 스캐너 미연결과 수동 시험을 표시한다. 실제 적용에는 스캐너 위치, 판독 완료 신호, 기대 ID의 출처, 운송 정지/회복 정책을 지정한 별도 연결이 필요하다.
- 제품 LOT 바코드와 재사용 트레이의 ID가 다르면 제품을 곧바로 containerCode로 등록하지 않는다. 이 프로필은 트레이/캐리어 ID 관리이며 LOT↔캐리어 이력은 별도 설계 대상이다.

## 검증과 한계

Fleet 2.15 공식 매뉴얼 670~673쪽과 677~679쪽의 containerQueryAll 및 설치된 Standard API 2.15.5의 addContainerAndEnter/moveContainer/departContainerAndRemove 구현을 기준으로 작성했다. 로컬 Java/C# 시험과 실제 라이브러리 간 loopback HSMS만 검증한다. 서버 권한·실제 포트 점유·스캐너·로봇 배차/운송은 사용자 적용 후 확인해야 한다. 외부 시스템이 동시에 재고/작업을 변경하는 경쟁 상태까지 이 플러그인의 조회만으로 원자적으로 잠글 수 없으며 최종 Fleet API의 거부도 처리한다.

재고 조회는 반드시 `containerQueryAll`을 쓴다. `containerQuery`는 반입 상태만 반환하므로 이를 신규/기존 구분에 쓰면 반출된 기존 화물을 신규로 오인한다.
