# 리프트 도중 FORCE 취소 시험 — 2026-10-30

## 결론

현재 설치된 Fleet의 공개 REST `missionCancel(cancelMode=FORCE)` 경로에서는 **실행 중 리프트가 중간에 정지하지 않았다. 상승·하강을 완료한 뒤 작업이 취소되고 차량이 해제됐다.**

WCS에 FORCE를 보냈지만 Mission Manager 수신 로그에는 `type: "NORMAL"`, 실행 로그에는 `Cancel mission: MILD`가 기록됐다. 이 결론은 현재 설치본과 아래 시험 경로에 한정하며, 모든 Fleet 버전이나 실제 차량의 모든 중단 수단이 불가능하다는 의미는 아니다.

## 시험 방법

- 기존 SIM01 / KMP1500i 가상 AMR2와 SIM_CARGO_001을 사용했다.
- 시뮬레이터가 리프트 요청을 수신한 로그(UP `0x0312`, DOWN `0x0314`)를 SSH로 감시하고 해당 시험 작업의 실행 중 C-step을 확인한 뒤 FORCE 취소를 한 번 보냈다. 변경 API 자동 재전송은 하지 않았다.
- 완료 시점의 `lift ... finish` 로그는 시작 트리거로 사용하지 않았다.
- 아래 시각은 모두 같은 서버 로그 시각이다. 서버 날짜는 2026-10-24로 설정되어 있어, 시험일인 PC 날짜 2026-10-30과 다르다. 서로 다른 장비 시계를 빼서 지연을 계산하지 않았다.

| 구분 | 하강 시험 | 상승 시험 |
|---|---|---|
| COMMANDID | LIFT_DROP_093210 | LIFT_PICKUP_093328 |
| Workflow ID | 6889 | 6890 |
| 시뮬레이터 리프트 요청 수신 | 09:12:49.382 | 09:14:03.325 |
| Mission Manager 취소 요청 수신 | 09:12:49.492 | 09:14:03.385 |
| 위 두 로그 사이 간격 | 110ms | 60ms |
| 리프트 완료 로그 | 09:12:50.319 | 09:14:04.318 |
| 취소 요청 수신 후 리프트 완료까지 | 827ms | 933ms |
| 취소 처리 모드 | NORMAL / MILD | NORMAL / MILD |
| 최종 작업 상태 | 31: 취소 | 31: 취소 |
| 최종 차량 적재 상태 | 하강 완료, 빈 차 | 상승 완료, 화물001 적재 |

PC에서 시작 로그를 관측한 뒤 취소 전송까지의 기록은 하강 약63ms, 상승 약47ms였다. 위 서버 수신 간격에는 로그 전달·조회·HTTP 처리 시간이 포함된다. 어느 수치도 물리적 리프트 정지 시간은 아니다.

## 전체 작업 정리

- 기존 일시정지 작업6886을 정확한 COMMANDID로 재개해 정상 완료·하차를 확인했다.
- 보정 시험6887은 완료 로그 직후 취소되어 **리프트 도중 시험에서 제외**했다.
- 단일 DOWN 구성 시험6888은 `Rack code cannot be empty`로 배차 실패했다. 리프트 요청이 발생하지 않았으므로 도중 시험에서 제외하고 해당 시험 작업만 취소했다.
- 유효 시험6889·6890은 위 표와 같다.
- 복구 작업6891 (`LIFT_RECOVER_093501`)에서 실제 시뮬레이터 하차 동작을 실행했고 상태30 정상 완료를 확인했다. 화물 메타데이터 강제 삭제·입출고 처리로 대신하지 않았다.

최종 조회: AMR1/2/3 모두 status3(Idle), occupyStatus0, liftStatus0, 적재 화물 없음. 대기 노드는 각각103/105/102다. 화물001은97번,002는98번,003은84번에 비적재 상태로 존재한다. SECS 활성 작업0, 대기 보고0, TSC는 기존 `PAUSED` 상태를 유지했다. 새 운송 전 Virtual MCS에서 운송 RESUME으로 AUTO 전환을 확인해야 한다.

## 구현에 대한 영향과 검증 범위

- 작업 취소 완료와 실제 리프트 동작 실패는 구분해야 한다. 이번 시험의 UP/DOWN은 성공 완료됐으므로 이를 무조건 ‘이적재 실패’로 보고하면 실제 상태와 어긋난다.
- 같은 FORCE 경로를 사용하는 ABORT 구현만으로 ‘리프트 즉시 정지’를 보장할 수 없다. 즉시 정지가 필수라면 실제 실행 중 이적재를 중단하는 별도 지원 수단을 확인해야 한다.
- 리프트 완료를 기다리는 동작을 허용할 경우, 완료 후 작업 취소·차량 해제·현재 적재 상태를 보고하는 별도 정책이 필요하다. 이는 시험 결과에 따른 제안이며 사용자 요구를 변경한 것은 아니다.
- 이번 시험은 **Fleet REST 제어와 가상 AMR 실행 로그 검증**이다. 새 플러그인1.1.7을 설치하지 않았고, 해당 버전의 S5F1/201/610 보고 순서나 호스트 ACK 흐름을 실서버에서 검증한 결과는 아니다.
- CANCEL·PAUSE 리프트 중 거부 로직도 이번 REST FORCE 시험과 별도다. 가상 시험 결과가 실제 차량의 안전 정지·기계적 동작을 보증하지는 않는다.
