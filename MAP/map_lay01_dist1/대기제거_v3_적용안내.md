# 대기 노드 제거 수정본

가져올 파일: `map_lay01_dist1_no_queue_v3.json`

기준: 사용자가 현재 Fleet에서 Export한 `map_lay01_dist1_o4h.json`.
원본 파일은 변경하지 않았습니다.

## 변경 내용

- 56, 57, 58, 59, 61, 65, 67, 68, 69, 70의 QUEUING_POINT 기능을 제거했습니다.
- 해당 점들은 일반 이동 노드로 남겨 경로 연결과 2m 간격을 보존했습니다.
- 68개 방향별 엣지 모두 Robot Direction `0,180`으로 통일했습니다.
- 27개 노드의 번호, UUID, 좌표, 68개 엣지의 연결을 보존했습니다.
- 작업장 10곳, 충전 입구 2곳, 충전소 2곳과 충전 연결 엣지를 보존했습니다.
- 기존 속도, 회전, 센서/회피, 자동주차 설정은 변경하지 않았습니다.
- 이전에 요구한 작업장 앞 대기는 최신 요청에 따라 제거했습니다. 임시 대기 영역도 생성하지 않습니다.

## 적용 순서

1. Workflow Event의 반복 이벤트를 비활성화합니다.
2. 가상 AMR에 남아 있는 정지/대기/실행 중 미션을 확인하고 취소합니다.
   Jobboard의 작업 수가 0이어도 Mission List에는 SUSPENDED 미션이 남을 수 있습니다.
   맵 파일은 미션 취소, 로봇 잠금 해제, 들고 있는 화물 상태 초기화를 수행하지 않습니다.
   들고 있는 화물은 현재 상태를 확인해서 처리하며, 기존 화물을 중복 생성하지 않습니다.
3. 기존 Layout `lay01`의 Import Layout File에서 위 JSON을 가져와 서버에 저장합니다.
   새 Layout을 만들거나 기존 Layout 자체를 삭제하지 않습니다.
4. 61번 등 이전 대기 노드가 일반 노드로 표시되는지 확인합니다.
5. 가상 AMR 한 대로 60 → 61 이동을 먼저 확인합니다. 확인 후 94 ↔ 96 운반을 진행합니다.
6. Workflow에 `robot queueing by RCS`가 설정돼 있다면 AS의 Exception Handling을
   `step queue up`으로 바꿉니다. 이 설정은 목적지가 점유되면 현재 위치에서 기다리며,
   앞 노드로 이동해서 대기하지 않습니다. 전용 대기 노드 없이 실행하기 위한 설정입니다.
7. 화물 위치와 Robot ID를 확인하고 왕복 Workflow를 한 번 실행합니다.
   처음 들기 단계부터 다시 실행할 때는 해당 로봇이 이미 화물을 들고 있지 않은지 확인합니다.
   왕복 성공 후 반복 이벤트를 활성화합니다.

## 검증과 한계

- 정적 방향별 경로 702쌍, 모든 엣지의 역방향 연결, 2m 간격, 고유 ID와 참조를 확인했습니다.
- 89 ↔ 97, 84 ↔ 86, 94 ↔ 96 및 60 → 61의 정적 경로가 존재합니다.
- 중앙 60, 63, 66을 통과하지 않고도 세 운반 구간의 경로가 존재함을 확인했습니다.
- Fleet 실제 Import, 충돌 회피 및 가상 AMR 실행은 아직 검증하지 않았습니다.
- 맵 JSON에는 Workflow/Event, Area, 로봇/화물의 현재 상태 및 서버 정책이 포함되지 않습니다.
- 현재 `Goal 61 In a queue`는 기존 맵의 61번에 대기 기능이 있고 기본 정책이
  대기 노드를 목적지로 허용하지 않을 때 나오는 메시지입니다. 수정본에는 그 기능이 없습니다.
- 이전 `PP_NoPath`의 모든 원인이 이 변경으로 해소됐다고 단정하지 않습니다.
- 근거: Fleet 2.15 매뉴얼 203쪽(Robot Direction), 327~329쪽(대기 노드의 목표/통과 제한),
  358쪽(Workflow의 step queue up). 실물 주행용으로 검증된 맵은 아닙니다.
