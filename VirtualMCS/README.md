# 로컬 빌드 · Virtual MCS 2.4.6 / 플러그인 1.5.8

2.4.6은 현재 작업이 한 건이면 자동 선택하고, 도착 포트 목록 조회 때 SV23도 함께 갱신한다. 목적지 버튼은 클릭 시 최신 작업 상태를 확인하며, 적재 전이면 전송 보류 사유를 표시한다. 1.5.7은 실제 WCS 기록에서 확인한 픽업 전 배차 차량 변경을 처리해 운송 상태 추적과 목적지 변경을 이어간다.

2.4.5는 우선순위와 목적지 UPDATE 버튼의 전송 경로를 분리한다. **도착 포트 목록 조회**로 받은 전체 PortID를 선택할 수 있고, 목적지 UPDATE에는 해당 작업의 현재 우선순위를 자동으로 넣는다. 로그의 **목적지 UPDATE 요청 · DESTPORT=...**에서 실제 전송 대상을 확인한다. 플러그인 1.5.6은 상태 응답 버전 표기를 수정하고 UPDATE 거부 원인을 CEID 9003으로 함께 보고한다.

2.4.4는 상태 조회 시험 창의 작업 목록 높이를 확보해 조회한 행을 선택할 수 있도록 수정했다. 목록에서 작업을 선택하면 해당 상태에 맞는 UPDATE 버튼이 활성화된다.

## 이송 중 목적지 변경 시험

1. Fleet 플러그인 1.5.8을 적용하고 `실행.cmd`로 Virtual MCS를 실행해 연결한다.
2. **상태 조회 시험 → 포트 조회 · SV58**에서 비어 있는 새 목적지의 PortID를 확인한다. AMR이 화물을 적재하고 기존 목적지로 주행하는 동안 **현재 작업 조회 · SV23**을 누르고 **운송 중**인 작업을 선택한다.
3. 새 PortID를 입력하고 **목적지 UPDATE 시험**을 누른다. 프로그램은 SV23과 SV58을 다시 읽고, 선택한 COMMANDID와 현재 우선순위, 새 DESTPORT를 전송한다.
4. `HCACK=4`는 접수다. `CEID 212`의 DESTPORT와 다시 조회한 SV23의 도착 포트가 새 포트인지 확인한다. 새 포트에서 하역한 뒤 `CEID 207`의 DESTPORT와 CarrierLoc도 확인한다. 거부 또는 실패는 `S2F42`와 `CEID 213`에서 확인한다.

## 배차 대기 중 우선순위 변경 시험

`실행.cmd`로 실행한 뒤 **상태 조회 시험 → 현재 작업 조회 · SV23**을 누른다. **현재 작업 · SV23** 탭에서 대기열 작업을 선택하고 새 우선순위 `1~99`를 입력한 뒤 **우선순위 UPDATE 시험**을 누른다. MCS가 SV23을 새로 조회한 뒤 같은 COMMANDID에 `S2F41 UPDATE`를 한 번 보낸다. Fleet이 배차 여부를 최종 확인한다. 목적지는 기존 값으로 유지한다.

시험 창에서 `S2F42 HCACK`와 최종 `CEID 212/213`을 각각 확인한다. `212` 수신 후 **현재 작업 조회 · SV23**을 다시 누르면 현재 우선순위를 볼 수 있다. SECS 우선순위는 99가 가장 높다. 결과를 기다리는 같은 작업에 대한 UPDATE는 차단한다. `전체 SECS` 탭에서 원문과 ACK도 확인할 수 있다.

## 2.4.1 배포 이력

Virtual MCS 2.4.1부터 `608 VehicleInstalled`와 `609 VehicleRemoved`를 차량 ID와 함께 표시하고 `S6F12 ACKC6=0`으로 응답한다. [Fleet 차량 설치·제거 시험 방법](../SECS/native_host/VEHICLE_INSTALLATION_1.5.4.md)

## 2.4.0 배포 이력

플러그인 배포 파일은 1.5.2를 사용한다. 1.5.1의 최종 파일에서 런타임이 빠진 패키징 오류를 바로잡고, 1.5.0 기능·전체 런타임과 아래 식별자 통일 수정을 포함했다. MCS 실행 코드 변경은 없다. [패키징 수정 안내](../SECS/native_host/PACKAGE_REPAIR_1.5.2_20261103.md).

2.4.0부터 **MCS가 보고받은 PortID·VehicleID를 변환 없이 요청·보고·이력에 사용**한다. 별도 MCS XML, 고정 PORT_xx 목록, AMR_ 접두어 생성/숫자 ID 변환은 사용하지 않는다. 접속 후 SV25/SV58을 조회해 FROM은 PortID+VehicleID, TO와 화물 포트는 PortID로 구성한다. 전송 직전에도 SV25/SV58을 다시 조회한다. 두 조회가 완료되지 않거나 실패하면 새 운송을 차단한다. 목록에서 사라진 선택 항목을 다른 포트/차량으로 임의 대체하지 않는다. **AGV·포트 다시 조회**로 읽기 전용 갱신이 가능하다.

- 일반 운송 예: SOURCEPORT=`lay01-dist1-98`, DESTPORT=`SECS_ST_89`.
- 회수반송 예: SOURCEPORT=`AGV002`, DESTPORT=`SECS_ST_89`. AMR_AGV002를 붙이지 않는다.
- 실제 포트 이름은 SV58의 값이 기준이다. 현재 Fleet에서 89/97은 외부 이름 SECS_ST_89/SECS_ST_97이고, 외부 이름이 없는 98은 lay01-dist1-98이다. SECS_ST_98을 임의로 만들어내지 않는다.
- Fleet 내부 정수 RobotID↔MCS VehicleID 설정은 플러그인이 책임진다. MCS 실행 폴더의 기존 Robot XML은 새 버전에서 읽지 않는다. API 서버 XML을 변경할 필요 없이 현재 보고 이름을 사용한다.
- 서버 1.5.1은 별칭을 받아도 작업 접수 시 포트를 canonical PortID로 확정하며, SV23/차량 TransferPort/CarrierLoc/완료 SOURCEPORT·DESTPORT에 같은 ID를 출력한다. 실제 Fleet nodeCode와의 연결도 동일 카탈로그에서 해석한다. 옛 저널 조회용 내부 별칭은 유지하지만 MCS의 새 요청에는 만들지 않는다.
- 과거 jobs.jsonl·원문은 소급 변경하지 않는다. 새 요청은 회수 차량의 정확한 VehicleID도 저장해 카탈로그 재조회/단절 후 다른 차량으로 잘못 매칭하지 않는다.

실행: `실행.cmd` 또는 `dist-2.4.0/KukaVirtualMCS.exe`. Visual Studio는 디버깅 종료 후 재빌드한다. 플러그인 Import는 사용자 진행이다. 기존 작업과 미확인 보고를 정리한 후 1.5.1을 적용하고 MCS를 다시 연결한다. 상태 조회 창의 VehicleID/PortID와 FROM/TO 값이 같은지 확인한다. 연결만으로 운송하지 않는다.

검증: canonical ID 전용 서버 13개 체크와 전체 플러그인 회귀/격리 로더 시험, MCS 카탈로그/앞자리0/회수 소유자/보고 상관관계/기존 로그·ACK 회귀, 실제 Java↔.NET HSMS 연결에서 S1F4 수신 ID→S2F49→14개 운송 보고→완료 이력 AGV001/SECS_ST_89/SECS_ST_97 일치 및 단일 제출을 확인했다. 모두 로컬 fixture/loopback이며 실제 Fleet 운송을 새로 실행한 증거는 아니다. 상세 적용: [식별자 통일 적용방법](../SECS/native_host/CANONICAL_ID_1.5.1_2.4.0_적용방법.md).

아래 XML 로딩과 PORT_xx/AMR_ 입력 설명은 이전 버전 기록이며 2.4.0의 동작이 아니다.

2.3.8은 **선택 작업 로그 보기** 버튼에서도 메모리뿐 아니라 저장된 로그를 읽고 S2F49 요청 원문을 선택한다. 이전에는 타임라인 행 클릭만 디스크 로그를 읽어, 재실행 후 버튼만 누르면 과거 원문이 없는 것처럼 보였다. 로그 창 하단 원문에 **원문 출처**를 표시해 현재 실행 기록인지 실제 저장 파일인지 구분한다. `messages_YYYYMMDD.log`와 `secs_YYYYMMDD.log` 양쪽을 조회하고 중복 메시지는 합친다. 저장된 원문 자체가 없으면 그 사실과 조회 폴더를 표시한다.

하단 원문은 선택된 `LogEntry.Text`이며 SECS 송수신 당시의 SML이다. 위쪽 COMMANDID/원문 출처 줄은 MCS가 붙이는 조회 정보로서 전송 필드가 아니다. S2F50 본문에는 COMMANDID가 없으므로 SystemBytes로 원 S2F49와 연결한다. 작업 상세·타임라인은 별도로 `jobs.jsonl`의 상태 변경 기록을 표시하므로, 이력만 남고 원문 파일이 없는 경우도 구분해야 한다.

2026-11-03 로컬 실제 기록 조사: 작업 `2722F07867AE46F1B2F7A8DEE18155BD`는 2026-10-29 메시지 파일에 S2F49/S2F50 2건이 있으며 실행 중인 2.3.7 화면에서 HCACK=2 원문까지 확인했다. 작업 `5B611530709544C086F4536873D8BC88`는 2026-10-27 메시지 파일에서 20건과 타임라인 11개 전체를 매칭했다. 작업 `80CBA959FFCE4F14A48178FB9CD3550A`는 작업 이력이 있으나 조사한 로컬 로그에 원문이 없다. 2026-11-02 메시지 파일은 10:35:42, SECS 통합 로그는 13:13:53에서 끝나 17:18 작업을 포함하지 않는다. 당시 저장되지 않은 이유는 현재 파일만으로 확정하지 않았다. 원문을 상태 이력에서 만들어내지 않는다.

2.3.7은 메인/별도 작업 이력 창의 **타임라인 행을 한 번 클릭하면 로그 창을 열거나 앞으로 가져오고 해당 SECS 메시지를 선택**한다. S2F49 전송 시도, S2F50 응답, 차량/화물/운송 이벤트는 COMMANDID·송수신 방향·메시지 종류·CEID와 기록 시각(2초 이내)을 대조한다. 같은 CEID가 반복돼도 기록 시각으로 구분한다. 과거 원문을 읽는 중 새 로그로 선택이 바뀌지 않도록 새 메시지 따라가기를 해제한다.

메모리에 원문이 없으면 `%LOCALAPPDATA%\ServoStar\KukaVirtualMCS\logs\messages_YYYYMMDD.log`를 백그라운드에서 읽는다. 프로그램을 다시 실행한 경우에도 저장 파일이 있으면 연결한다. S2F50처럼 본문에 COMMANDID가 없는 응답은 같은 SystemBytes의 원 요청과 연결한다. 저장 로그는 수정하거나 재전송하지 않는다. 시각/원문이 없거나 재시작·수동 대기 해제 등 통신 메시지가 아닌 행이면 원문 미확인 사유를 표시하고 다른 메시지를 대신 선택하지 않는다. 연속 클릭 시 마지막 요청만 화면에 반영한다.

기존 MCS를 종료하고 Visual Studio에서 다시 빌드/실행하거나 `dist-2.3.8/KukaVirtualMCS.exe`를 사용한다. Fleet 플러그인 재Import는 필요 없다. 실제 타임라인 마우스 이벤트→로그 선택, 메모리 비운 뒤 디스크 원문 조회, S2F50 응답 상관관계, 반복 CEID, 원문 없음 표시와 기존 회귀 시험을 로컬로 확인했다. 실제 Fleet 운송은 새로 발행하지 않았다.

2.3.6은 작업 이력 영역 오른쪽 **작업 이력 새 창**으로 목록·작업 상세·상태 타임라인을 별도 창에서 볼 수 있다. 메인 화면의 동일한 행 데이터와 선택 항목을 WPF 바인딩으로 연결하며, 별도 JobStore/통신 연결을 만들지 않는다. 어느 창에서 작업을 선택해도 다른 창의 선택과 상세 정보가 함께 바뀌고, 상태·배차 AGV·CEID·결과·미확인 작업 수가 기존 수신 처리에 따라 갱신된다. 목록 범위는 메인과 같은 최근 200건이다.

별도 이력 창의 **선택 작업 로그 보기**를 누르면 실시간 로그 창을 열고 해당 COMMANDID로 필터링한다. 로그 창의 **작업 선택 연동**을 켜면 메인/별도 이력 창의 선택을 계속 따라가며, 직접 COMMANDID 필터를 편집하면 연동을 해제해 입력값을 유지한다. 창 닫기/다시 열기는 작업 선택과 기존 통신을 유지한다. 이력 창에서는 조회와 복사만 제공한다.

Visual Studio에서는 기존 디버깅을 종료한 뒤 다시 빌드/실행한다. 배포 실행 파일은 `dist-2.3.8/KukaVirtualMCS.exe`이며 Fleet 플러그인 재Import는 필요 없다. 메인↔별도 창 선택, 상태 변경 후 선택 유지, 상세/타임라인 갱신, 선택 작업 로그 필터, 수동 필터 유지, 닫기·다시 열기를 오프라인으로 검증했다. 실제 Fleet 운송은 이 기능 검증을 위해 새로 발행하지 않았다.

2.3.5는 메인 로그 영역 오른쪽 **로그 새 창**으로 실시간 로그를 별도 창에서 볼 수 있다. 작업 메시지/전체 SECS/연결·시스템/전체 로그를 전환하고 COMMANDID 일부 검색, 새 메시지 따라가기, 원문 줄바꿈/복사와 로그 폴더 열기를 제공한다. 목록과 원문 사이 구분선을 끌어 높이를 조절하고 창 크기/위치를 독립적으로 변경할 수 있다. 최근 로그 3000건을 보관하며 디스크 로그 저장은 기존대로 유지한다. 메인 화면의 화면 로그 지우기는 별도 창의 로그도 함께 지운다.

창을 열 때 현재 메인 탭과 선택 작업 필터를 가져오고, 이후에는 별도 창에서 독립적으로 필터를 변경한다. 다시 버튼을 누르면 기존 로그 창을 앞으로 가져온다. 로그 창을 닫아도 MCS 통신은 유지되며 다시 열 수 있다. 기존 **원문 크게 보기**는 선택 메시지 한 건을 보는 기능으로 유지한다.

실행은 `실행.cmd` 또는 `dist-2.3.8/KukaVirtualMCS.exe`. Visual Studio에서는 기존 디버깅을 종료하고 다시 빌드/실행해야 새 버튼이 표시된다. 실행 중인 이전 MCS를 자동 종료하거나 교체하지 않는다. 별도 창의 실시간 추가/필터/따라가기 해제/닫기·다시 열기와 화면 렌더링은 오프라인으로 검증했다.

2.3.4는 플러그인과 동일한 Robot XML을 읽는다. 실행 파일 옆 `servostar-robot-names.xml`을 시작할 때 읽으며, **Robot XML 불러오기**로 파일을 선택하면 검증 후 실행 폴더의 이 파일로 복사한다. 파일을 직접 수정했으면 **XML 다시 읽기**를 누른다. 불러오기/다시 읽기는 연결 해제 및 로컬 미확인 작업 정리 후 가능하다. 기존 작업의 식별자와 수신 SECS 원문은 다시 매핑하지 않는다.

- 현재 실행 파일: `C:\work\KUKA\KUKA_Fleet\VirtualMCS\dist-2.3.8\KukaVirtualMCS.exe`
- MCS가 실제로 읽는 XML: `C:\work\KUKA\KUKA_Fleet\VirtualMCS\dist-2.3.8\servostar-robot-names.xml`

# KUKA Virtual MCS 1.x 기록

기존 SKI VirtualMCS의 연결 버튼 / From·To 운송 생성 / 작업 목록 구성을 참고해 만든 별도 Windows WPF 프로그램이다. 기존 소스와 AIM DLL은 수정하거나 복사하지 않았다. 새 프로그램은 Secs4Net 3.1.0으로 HSMS/SECS를 직접 송수신한다.

## 실행

`실행.cmd` 또는 `dist-1.4.0/KukaVirtualMCS.exe`를 실행한다. Windows x64와 .NET 10 Desktop Runtime이 필요하다. 이 PC에는 해당 런타임이 설치되어 있다. 다른 PC로 옮길 때는 EXE만 복사하지 말고 `dist-1.4.0` 폴더 전체를 복사한다.

1. SEComSimulator의 Open Connection을 닫는다. 기존 연결이 남은 상태에서 같은 Fleet 포트에 경쟁 접속하지 않는다.
2. 기본값 `192.168.0.45 / 5556 / Session 3000 / PC Active / T3 120초`를 확인하고 **연결**을 누른다. Passive 선택 시 IP는 PC의 로컬 바인딩 주소이며 Fleet도 대응하는 Active 설정이어야 한다. 현재 시험은 기본 Active를 사용한다.
3. HSMS Selected 후 S1F13을 자동 전송한다. 우측 상태가 **COMMUNICATING**이면 운송 버튼이 활성화된다. 필요할 때 S1F13/S1F17 버튼을 별도로 사용할 수 있다.
4. Fleet에서 `SIM_CARGO_001`의 실제 위치를 확인하고 **89 → 97 전송**, **97 → 89 전송** 또는 From/To 선택 후 **선택 경로 전송**을 한 번 누른다.
5. COMMANDID는 매 작업마다 32자 GUID로 자동 생성한다. 직접 편집할 필요가 없다. REPLACE=0 고정, PRIORITY 1~99이다.

## 작업과 보고

- S2F49 구조는 현재 Fleet ECS에서 사용하는 COMMANDINFO / TRANSFERINFO의 이름-값 쌍 형식이다. 플러그인 0.5.0 + Reports06에서는 KMP1500I AMR 1/2/3 중 Fleet이 자동 배차한다. 1.4.0 + 플러그인 0.6.0 + Reports07은 SIM_CARGO_001을 작업 포트 10개 사이에서 운송한다. 아래 1.4.0 적용 절을 확인한다.
- S2F50 단일 B=0과 L[2] HCACK 형식을 모두 읽는다. 현재 Fleet은 운송 API 결과가 나오기 전에 B=0을 응답하므로 **응답 수신을 운송 접수·완료로 표시하지 않는다**. 서버가 이후 거부하면 이 프로그램에는 완료가 없을 수 있다.
- S6F11 RPTID2에서 COMMANDID·화물·출발·도착이 일치하는 보고만 작업에 반영한다. CEID208 시작, 211 진행, 207 완료/비정상 종료를 구분한다. 정상 207은 Result=0과 최종 CarrierLoc=도착 포트가 모두 맞아야 완료로 표시한다.
- 수신 S6F11에는 S6F12, S5F1에는 S5F2를 자동 응답한다. 형식이 잘못된 S6F11은 ACKC6=1로 응답한다. ACK는 메시지 수신 처리 결과이며 실제 운송 완료 판정과 다르다.
- **완료 보고 후 From/To 교환**이 체크돼 있으면 정상 207 수신 후 입력 방향만 바꾼다. 반대편 운송을 자동으로 보내지 않는다. 다음 버튼 클릭에서 새 ID를 만든다.
- 미확인 화물 작업이 있으면 추가 전송을 차단한다. 중복 클릭·T3 타임아웃·연결 복구 때 S2F49를 자동 재전송하지 않는다. 응답 유실/연결 단절/프로그램 재시작 후 미완료 건은 상태 확인 필요로 남긴다.
- 완료 보고가 안 오거나 서버에서 거부한 경우, Fleet에서 기존 작업 상태와 실제 화물 위치를 먼저 확인한다. 그 뒤 작업 목록에서 해당 건을 선택해 **현장 확인 후 대기 해제**를 누르면 로컬 추가 전송 차단만 해제한다. 이것은 Fleet 취소 명령도, 운송 완료 처리도 아니다.
- S5F1 알람은 로그에 별도 표시한다. 서버가 보고하지 않는 진행·완료·abnormal 정보를 생성하지 않는다. CANCEL/ABORT/RESUME, 자동 반복 운전, Fleet 설정 수정은 구현하지 않았다.

## 1.0.2 메시지와 작업 상세

- 기본 **작업 메시지** 탭에는 운송 요청/응답, 시작 208, 진행 211, 완료 207, ACK, 알람을 표시한다. LinkTest와 연결 로그가 섞이지 않는다. 시작은 파랑, 진행은 갈색, 완료 보고는 초록으로 구분한다. 보고의 Result 값은 별도로 확인한다.
- **전체 SECS** 탭에는 S1F13 등 기본 통신까지 포함한 TX/RX 메시지를 표시한다. 방향 / S·F / CEID / 설명 / COMMANDID / SystemBytes를 각각 열로 볼 수 있다.
- 행 선택 시 아래에 원문이 표시된다. **더블클릭** 또는 **원문 크게 보기**를 누르면 복사 가능한 별도 창이 열린다. 목록과 원문 사이 분리선을 끌어 높이를 바꿀 수 있다.
- **선택 작업만**을 체크하면 작업 이력에서 선택한 COMMANDID의 메시지와 ACK만 표시한다. **새 메시지 따라가기**를 끄면 이전 메시지를 검토하는 동안 선택을 유지한다.
- 작업 이력을 **더블클릭**하거나 **선택 작업 상세**를 누르면 작업 상세 탭으로 이동한다. 전체 ID, 화물, 경로, 상태, 생성 시각, 시작/진행/종료 보고 시각, 상태 타임라인을 볼 수 있다.
- 새 버전부터 각 작업 상태의 실제 기록 시각을 jobs.jsonl에 저장한다. 이전 버전 기록도 읽지만 시각이 없는 과거 보고에 시간을 만들어 넣지 않는다. 메시지 목록은 이번 실행에서 수신한 최근 2,000건이며, 과거 작업 상태는 jobs.jsonl에서 복구한다.
- 메시지 원문은 logs/messages_yyyyMMdd.log에도 별도로 저장한다. 기존 통합 secs 로그도 유지한다. 화면 로그 지우기는 작업 이력과 파일을 삭제하지 않는다.
- 로컬 HSMS 회귀 검사와 메시지/응답의 COMMANDID 연결, 타임라인 보존/재시작/과거 기록 호환을 합쳐 49개 검사를 통과했다. 새 UI는 오프라인 예시 프로필로 렌더링해 확인하며 실제 Fleet에 운송을 보내지 않는다.
